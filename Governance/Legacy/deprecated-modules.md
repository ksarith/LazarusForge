deprecated-modules.md

Legacy Module — Superseded Operational Logic, Retired Module Structures, and Architectural Evolution in LazarusForgeV0

---

1. Purpose
The Deprecated Modules file preserves the full historical record of operational modules that were once active in LazarusForgeV0 but have since been:

- replaced,  
- superseded,  
- merged,  
- retired for safety,  
- invalidated by architectural evolution,  
- or rendered obsolete by constitutional governance.

Deprecated modules cannot influence current architecture.  
They exist solely for provenance, historical insight, and institutional memory.

---

2. Scope
This module governs:

- modules removed from active operation  
- modules replaced by more mature versions  
- modules deprecated due to safety concerns  
- modules invalidated by verification failures  
- modules retired due to architectural restructuring  
- modules rendered obsolete by canonical evolution  

This module does not govern:

- active operational modules  
- constitutional governance  
- verification gates  
- unknown lifecycle rules  

Those are defined in higher layers.

---

3. Deprecation Principles
Deprecated modules follow five principles:

- Non‑Interference — deprecated modules cannot affect active logic.  
- Provenance Preservation — all module history must be retained.  
- Safety Alignment — unsafe modules must be clearly marked.  
- Contextualization — deprecation must include justification and historical context.  
- Traceability — module ancestry and replacement must be documented.

These principles ensure safe and meaningful archival.

---

4. Deprecation Categories
Modules may be deprecated for several reasons:

4.1 Superseded Modules
Modules replaced by more mature or safer versions.

4.2 Safety‑Deprecated Modules
Modules retired because they:

- violated safety boundaries  
- created safety unknowns  
- enabled unsafe revival or reconstruction  
- triggered oversight intervention  

4.3 Verification‑Failed Modules
Modules deprecated because they:

- failed verification gates  
- lacked evidence  
- contained unresolved unknowns  
- produced unstable reasoning trails  

4.4 Obsolete Modules
Modules that no longer matter due to:

- architectural restructuring  
- consolidation of module responsibilities  
- removal of dependent systems  

Each category must include provenance and deprecation justification.

---

5. Deprecation Structure
Each deprecated module must follow a consistent archival structure:

`

Module Name (Deprecated)

Original Purpose
Explain what the module was designed to do.

Category
Superseded / Safety‑Deprecated / Verification‑Failed / Obsolete

Reason for Deprecation
Explain why the module was deprecated.

Provenance Record
List evidence, reasoning trails, unknown lifecycle records, and oversight decisions.

Architectural Impact
Describe how the module influenced the Forge historically.

Replacement (if applicable)
Link to the module or rule that replaced it.

Deprecation Date
YYYY‑MM‑DD
`

This structure ensures clarity and historical continuity.

---

6. Provenance Requirements
Deprecated modules must preserve:

- original module content  
- change history  
- reasoning trails  
- evidence lineage  
- unknown lifecycle records  
- oversight decisions  
- deprecation justification  
- architectural ancestry  

Provenance ensures epistemic accountability.

---

7. Safety Requirements
Modules deprecated for safety reasons must be clearly marked:

- Safety‑Deprecated  
- Unsafe Revival Path  
- Unsafe Reconstruction Logic  
- Emergent Behavior Risk  
- Verification Failure  

Safety markings prevent accidental reuse.
